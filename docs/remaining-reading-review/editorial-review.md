# 남은 운세·관계 해설 편집 검토

검토일: 2026-11-04. 이 문서는 원고 품질 검토와 제한된 코드 수정의 증거를 구분한다. 새 유료 생성·배포는 수행하지 않았다. 기존 저장 결과의 출생정보·상대정보·원문은 이 문서에 복사하지 않는다.

## 1차: 원인과 질문별 합격 기준

읽은 코드: `periodNarrativeV23.ts`, `promptV23.ts`, 관계 해설 `index.ts`, `relationship-quality-audit.mjs`, `relationshipUserSummary.ts`, 기존 저장 원고 검토 기록. 함수명과 경로는 아래에 구체적으로 기록한다.

### 확인한 문제

1. 기존 기간 프롬프트는 주간 초·중·후반과 연간 네 분기를 필수 순서로 요구했다. 동시에 근거가 있는 구간만 쓰라고 요구하여 자료가 적은 경우 지시가 충돌했다. 분야·시기·예외의 개수를 채우는 일이 해설의 목적이 되어서는 안 된다.
2. 기존 궁합 프롬프트의 overview 7~10문장, 세부 4~7문장 요구는 첫 화면 요약과 상세의 역할을 나누지 못했다. 결혼 모드는 공통 궁합 필드와 결혼 전용 필드를 함께 요구했고, 일반 궁합에도 reunion_context를 채우게 했다.
3. 검수는 존재하는 근거 ID·문자열 길이·표면 중복을 확인했지만, 하루 근거를 분기 전체로 늘린 주장이나 조건부 조언을 실제 상대 심리로 바꾼 문장을 충분히 차단하지 못했다.

### 실제 구버전 저장 결과 확인

비공개 QA 계정의 주간 1건·월간 1건·연간 1건·일반 궁합 1건을 읽었다. 새 계약의 생성 결과가 아니며, 입력 계산 전체가 없는 결과는 근거의 실제 천문학적 의미까지 검증했다고 주장하지 않는다.

| 표본 | 관측 결과 | 편집 판정 |
|---|---|---|
| 주간 | 초반 협의와 주말 피로를 구분하지만 일부 분야는 비어 있고, 조건 필드가 일반 생활 조언으로 채워짐 | 구조와 문장 품질을 별도로 검증해야 함 |
| 월간 | 기술어가 총평에 노출됨. 학업·대인 대표 원고는 빈 상태. 증상과 회복 효과를 관측한 것처럼 쓰는 문장 포함 | 빈 상태를 생성 누락과 근거 부족으로 구별해야 함 |
| 연간 | 2·3월 근거로 하반기 업무 안정화를 주장. 학업의 하루 best 날짜로 4분기 전체 업무 마무리를 설명 | 기간과 분야를 넘어선 근거 사용. 출고 차단 사례 |
| 일반 궁합 | 7문장 총평에 기술어가 반복됨. 요청하지 않은 재회 문맥, 상대의 실제 심리 추정, 임의의 냉각 시간 포함 | 모드별 질문과 해석/예시/관측 구분 필요 |

세 기간 표본 모두 저장된 자동 품질 점수는 100점이었다. 따라서 자동 점수를 실제 독해·기간 추론 검수의 대체물로 사용할 수 없다.

### 질문별 합격 기준

| 모드 | 독자에게 답해야 하는 질문 | 불합격 사례 |
|---|---|---|
| 주간 | 이번 주 무엇이 유지되고, 근거가 있는 어느 시점에서 무엇이 달라지는가? | 일일 조언의 기간명만 변경, 변화가 없는 자료에 초중후반 전환 생성 |
| 월간 | 반복되는 문제가 무엇이며 일시적 날짜와 한 달의 배경을 어떻게 구분하는가? | 하루 고점을 월 전체로 확대, 단순 표본 간격을 지속 기간으로 표현 |
| 연간 | 장기 배경과 특정 달의 촉발을 어떻게 나누고 무엇을 우선할 것인가? | 학업 하루 근거로 분기 업무 전망 작성, 근거 없는 네 분기 채우기 |
| 궁합 | 무엇이 끌리고, 생활에서는 어디가 맞거나 부딪히며, 갈등을 어떻게 다루는가? | 총평·끌림·갈등에서 같은 안전문구 반복, 실제 속마음·재회 시기 단정 |
| 미혼 결혼 | 관계를 공식화하기 전에 생활·역할·공유자원에서 무엇을 합의해야 하는가? | 관계 배치를 프러포즈 사건이나 결혼 날짜로 변경 |
| 기혼 결혼 | 현재의 역할·정서 거리·반복갈등·회복에서 무엇을 살펴야 하는가? | 결혼 성사 가능성을 다시 예측, 미혼과 제목만 다른 본문 |
| 재회 | 입력된 관측 상태는 무엇이고, 계산에서 확인된 다음 단계와 아직 확인되지 않은 단계는 무엇인가? | 감정 활성→연락→만남→재결합 자동 승격, 이미 연락한 기록을 미래 연락 예측으로 대체 |

공통 기준: Gemini가 핵심·이유·행동·필요 조건을 작성한다. UI와 저장 이미지는 같은 원고 블록을 사용한다. 핵심은 짧고 상세는 질문에 답할 만큼 충분해야 하며, 글자 수를 채우기 위한 일반론·임의 예외·중복은 불합격이다. 기존 기능이 미생성됐다는 이유로 지원 항목 자체를 없애지 않는다.

## 긴급 일일 세부항목 복구

사용자의 연락운 누락 지적으로 구현 범위를 추가했다. 소유 파일은 `dailyEditorialV1.ts`, `dailyReadingContractV1.ts`, `dailyRewriteV1.ts`와 해당 검사 파일이다. 상위 index·provider schema·UI는 다른 담당과 조율했다.

- 기존 25개 `EDITORIAL_SECTION_KEYS`를 그대로 사용한다. 새 세부항목이나 공개 상태 enum을 추가하지 않았다.
- 기본 6개는 첫 화면 우선순위다. 연락 활성·연락 지속·재회 관심·시험·이직·투자심리·수익실현·신규진입·소식 9개는 해당 날짜의 분야 근거가 있으면 명시적 작성 또는 명시적 불충분 응답이 필수다.
- 나머지 상태별 애정·대인 10개는 상황별 조건부 질문으로 유지한다. 근거와 별도 답이 없는 상태의 장문을 강제로 생성하지 않는다. 생략은 기존 `editorial_delivery=omitted`로 남기며, 생성된 불충분 응답과 구별한다.
- 모든 지원 질문의 원 근거를 writer packet에 보존한다. 다른 날짜 근거로 필수 세부항목을 활성화하지 않는다. 연락 질문을 연애 근거만으로 대신한 경우를 검출한다. 주제 정보가 없는 독립 체계 근거까지 무조건 다른 분야라고 배제하지는 않는다.
- 실제 세부항목 누락은 provider 정규화 전 구조검사에서 실패한다. 문장 편집 단계는 누락 항목을 새로 창작하거나 근거를 바꾸지 못한다.
- 일일 예외는 빈 문자열을 유지한다. 선연락·실제 재결합·가격·수익·합격·채용 결과로 확대하지 않는다.

### 비용·분량 검토

기존 가상 프로필 production-2 계산을 다시 읽어 로컬에서만 확인했다. 원 계산 205개 근거에서 writer packet은 78개 근거/35,189 bytes이며, 상위 prompt budget은 80,172/180,000 bytes로 통과했다. 기본 6개와 세부 9개가 필수 대상으로 분류됐다.

문장 의미가 없는 크기 전용 fixture로 결론 35자·이유 80자·행동 35자 × 15개와 총평·체계·focus·decision·window를 구성하면 JSON 13,891 bytes다. 기존 bytes/2.6 방식의 거친 추정은 5,343 tokens다. **Gemini 실토큰 수나 생각 토큰을 측정한 값이 아니다.** 긴 조건이나 선택 세부항목이 추가되면 기존 8,200 출력 한도를 넘을 수 있으며, 상한 통과를 보장하지 않는다. 추가 호출·비용 상한 증액은 하지 않았다.

## 2차: 구현 교차 검토

### 기간 해설

`periodReadingContractV1.ts`의 근거별 질문/생성 상태, 필수 시기 개수 제거, 하루·양 끝 표본으로 분기 범위를 만들지 못하게 하는 검사, 다른 분야 근거와 하반기 주장 검사를 확인했다. `qualityV2.ts`의 새 옵션은 해당 기간 계약에서만 강제 분량을 완화하고, 종전/일일 기본 검사를 보존한다. index의 정규화 전 provider 검사와 최종 품질 gate 연결도 확인했다.

잔여 한계: 자연어 월·전환 표현 전체를 파싱하지 않는다. 상·하반기 안의 한 날짜가 있다는 것과 반기 전체가 지속된다는 것은 다르다. 현재의 좁은 검사만으로 모든 기간 추론을 검증했다고 주장하지 않는다.

### 관계 해설

`relationshipEditorialV1.ts`의 핵심 역할 분리·분량 상한·모드 일치 검사, 일반 궁합과 결혼 중복 원고 제거, 관측 상태 귀속과 방향 검사 확장을 확인했다. `core_conditions` 최소 1개 강제는 과거 일일의 임의 예외 생성 문제와 같으므로, 필수 조건은 보존하되 없는 조건은 빈 배열로 허용하도록 담당에게 요청했다.

잔여 한계: 자연어 월·분기 날짜와 실제 속마음 추정의 의미 전체는 자동검사로 보장되지 않는다. 옛 저장 결과를 새 계약의 통과 사례로 계산하지 않는다.

### 로컬 검증

일일 계약·편집·제한 수정 및 prompt 검사 49개 통과. 연락 두 질문의 복구, 25개 기존 키 일치, 근거 있는 세부 누락 실패, 생성 누락/명시 불충분 구별, 무관 분야 근거 거부, 다른 날짜 근거 제외, 문장 편집의 범위 보존을 포함한다. 이 결과는 실제 Gemini 원고 검증이 아니다.

## 3차 상태 및 출고 조건

새 계약으로 생성한 주간·월간·연간·궁합·미혼·기혼·재회 원고와 복구된 일일 상세 원고는 아직 없다. QA 계정 생성 한도에 도달한 상태이며 이 담당은 유료 호출을 하지 않았다. 새 원고의 3차 독해와 실제 모바일/저장 이미지 확인은 **미완료**다.

새 원고를 생성한 후에는 (1) 질문에 바로 답하는 핵심, (2) 입력 근거와 기간·분야 일치, (3) 필수 조건의 요약 보존, (4) 상세 항목의 미생성 상태, (5) 화면과 저장 이미지의 동일 원고를 함께 확인해야 한다. 그 전까지 원고 품질 완성이나 production release를 승인하지 않는다.
